## 一、与 Phase3 代码的衔接核验（code-aware 检查）

方案自称"Phase3 code-aware revision"，我核对关键衔接点：

| 方案假设                               | Phase3 实际代码                                              | 核验                                                         |
| -------------------------------------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| `AgentSessionKey` 已作为 identity 使用 | `session.AgentSessionKey` ✅                                  | 一致                                                         |
| per-AgentSession lane 串行             | `ExecutionLane` ✅                                            | 一致                                                         |

| TurnTracer 暴露 turn_id 的方式待收敛   | 当前 `turnTracer` 是私有结构，`NewTurnTracer` 返回 `TurnTracer` **接口**（无 TurnID() 方法） | ⚠️ 方案 §7.5 正确识别了这个缺口，方案 A（接口加方法）vs 方案 B（显式 turnID 注入）二选一 |

**§7.5 的 turn_id 来源问题是本方案最有价值的前置识别**——Phase3 里 turn_id 在 `NewTurnTracer` 内部生成、外部不可见，Memory 要引用它必须改造。方案没有回避这个事实，明确列为"开工必须先补齐"，很好。

## 二、P1 问题（建议开工前定）

### P1-1：Context Scope Contract 表格有一个缺口——`Runtime Policy` 的 scope 只有"Runtime"，但权限/策略边界未定义

§5 表格第一行：

```text
| Runtime Policy | Runtime | Runtime config | P0 |
```

"Runtime Policy" 概念上包含了 Phase2 的 prompt 配置（language/style/tool_instruction）——但这些是**每个 Agent 可以不同**的（不同 NPC 说话风格不同）？还是全局统一的？表格没回答。

**建议**：明确 `Runtime Policy` 的 scope 是 `runtime`（全局）还是 `game_id + entity_id`（per-agent）的覆盖语义。Phase4 不用实现覆盖，但 Contract 要说明"当前全局唯一，未来 per-agent 覆盖时 scope 变更为 `game_id + entity_id`"。

### P1-2：`MemoryRecord.SourceTurnID` 方案 A vs B 没有拍板，但 §18.1 的 AgentLoop 改造暗示了方向

§7.5 列了方案 A（TurnTracer 暴露 ID）和方案 B（显式注入 turnID），说"可选实现"，但 §24 实施顺序第 3 步"补齐稳定 turn_id 来源"没选。

**建议拍板方案 B**（先 `idgen.New("turn")` 再传给 tracer）：它让 turn_id 在 AgentLoop 层可见、Memory 和 Trace 同源，比给接口加方法侵入性更小，且不破坏 `TurnTracer` 接口现有契约。方案 B 与 §7.5 "TraceEvent.turn_id == MemoryRecord.SourceTurnID" 的验收要求天然一致。

### P1-3：`MemoryStore.Append` 的失败语义与 `context_update_failed` 的 trace 时序有细节需要定死

§9.3 说：

```text
Memory Append 失败 → context_update_failed → Turn 仍保持 completed
```

但 §15 说：

```text
context_updated / context_update_failed 必须发生在 terminal turn event 之前
```

组合起来：**如果 Append 失败，trace 顺序是 `action_result_received → context_update_failed → turn_completed`**。这个顺序方案隐含了但没显式写。建议 §9.3 或 §15 补一句明确时序，避免实现时把 `context_update_failed` 放在 `turn_failed` 之后（那就违反"terminal 是最后一个事件"的 TurnTracer 不变量）。

### P1-4：TestEnvironment 的抽取边界——"从现有 gateway tests 抽取 helper"与"新建 testkit 包"的决策点没给标准

§17.1 说"先从现有 tests 抽取，再判断是否需要提升为独立 testkit"，§18 说"不要为目录形式提前创建空 package"。**方向正确，但缺一个明确的决策标准**：什么信号出现时才算"值得独立 testkit"？

**建议给一条硬标准**：当 ≥2 个测试文件（如 memory 集成测试 + 后续 Phase5 测试）需要复用同一套 bufconn+scripted adapter 装配代码时，就抽 `runtime/internal/testkit`。单测文件内私有 helper 不抽。

## 三、P2 问题（可接受，记录即可）

```text
1. §6.2 AgentContext 的 EventContext / ObservationContext 是"示意"，
   "最终是否直接用 Protocol 类型由 Phase3 代码 review 后决定"——合理，
   但建议给出倾向（直接用 *protocolv1alpha2.GameEvent / Observation，

2. §22 的集成测试清单很全（8 类），但没有明确它们跑在 testkit 上还是
   现有 gateway test helper 上——如果 TestEnvironment 抽取滞后，
   这些测试的落点会变。建议与 P1-4 联动：先定 testkit 决策，再写测试。

3. §28.4 承认 Stardew 交互信息有限（没有自然语言输入）——诚实且正确。

   建议在验收记录里明确这条预期，避免真机测试时对"模型没提起上轮内容"
   误判为失败。
```
