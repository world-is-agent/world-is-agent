# 1. P1：Phase5 缺少正常的 Turn settle 语义

Phase5 已经明确了：

```text
1 Turn = N AgentSteps
max_steps
Turn 全局 timeout
Tool Result 进入下一次模型请求
唯一 terminal result
```

但当前只说明了：

```text
超过最大步数时 Turn 明确收敛
```

没有说明一个 Multi-step Turn **如何在尚未达到 `max_steps` 时正常完成**。

这是 Phase5 唯一比较实质性的缺口。

例如：

```text
Step 1
    inspect / observe-like tool

Step 2
    speak

然后呢？
```

Runtime 必须知道：

```text
继续下一 Step
还是
当前 Turn 已经 settled
```

否则实现时容易临时选择：

```text
模型没有 ToolCall 就结束
显式 finish Tool
每次 Action 成功就结束
到 max_steps 强制结束
```

这些方案的语义完全不同。

Roadmap 不需要现在选定具体实现，但必须把问题纳入 Phase5 范围。

### 建议在 Phase5 主要范围增加

```markdown
- 明确 AgentStep 的 continue / settle / fail 控制语义；
- 正常 Turn 应能够在未达到 max_steps 时主动 settle；
- 具体使用无 ToolCall、显式 finish Runtime Tool 或 Runtime control policy，由 Phase5 技术方案确定。
```

### 完成条件增加

```markdown
- AgentTurn 可以通过 provider-neutral 的 settle 语义正常结束，而不是只能依赖 max_steps 或 timeout 被动终止。
```

这样 Phase5 才完整回答：

```text
怎么进入下一 Step？
怎么正常结束？
怎么失败？
怎么防止无限循环？
```

# 2. P1：Architecture checks 不应等到 Phase8

当前 Phase8 范围才包含：

```text
Architecture checks 与 CI gates
```

完成条件也要求：

```text
架构依赖违规能够自动阻止合并
```



但是 Roadmap 同时已经把这些列为跨阶段不变量：

```text
Runtime owns cognition
Protocol owns contracts
Adapter owns translation

EnvironmentSession != AgentSession
Capability != Policy != Tool
Observer != Functional Hook
```

并要求任何阶段破坏它们都必须先形成 Architecture Decision。

如果一直到 Phase8 才自动检查，那么 Phase3–Phase7 期间仍然主要靠人工记忆维护 Architecture v0.2。特别是 Phase3 会大量修改 Adapter 映射、多 NPC 路由和 Runtime identity，是最容易出现边界泄漏的阶段。

不需要把完整 CI 产品化提前，但最小 architecture check 应从现在开始成为跨阶段要求。

### 建议修改第 12 节“每阶段固定交付物”

增加：

```markdown
6. Architecture boundary check 与 protocol generated-code consistency check。
```

或更具体地写：

```text
每个 Phase 至少确认：
runtime 不依赖 adapters/
adapter 不依赖 runtime/internal/
runtime 不引用具体游戏 API
protocol generated code 与 proto source 一致
```

### Phase8 保留但改名

将：

```text
Architecture checks 与 CI gates
```

改为：

```text
完善 Architecture checks，并将其固化为完整 CI merge gates
```

这样阶段关系变成：

```text
Phase3 起
    已有最小架构保护

Phase8
    完善、标准化并产品化 CI gates
```

这更符合“Architecture Baseline 已经确定”的状态。

# 3. P1：Phase4 的持久化边界需要进一步收紧

Phase4 当前写：

```text
第一版优先使用 In-Memory Store 或简单本地持久化
```

而 Phase7 的核心范围又包括：

```text
AgentSession 与必要 Agent State 的持久化
跨进程重启保留
```



这两个阶段并不必然冲突，但“简单本地持久化”容易让 Phase4 技术方案逐步扩张成：

```text
文件格式
启动恢复
版本兼容
损坏处理
跨进程 Memory 恢复
```

从而提前进入 Phase7。

### 建议把 Phase4 这句话改成

```markdown
第一版默认使用 In-Memory Store。

如为开发调试或接口验证使用简单本地文件实现，该实现不承诺跨进程恢复、版本兼容或 Environment Recovery；正式的持久 Agent State 与重启恢复仍属于 Phase7。
```

另外，这句：

```text
在 Turn 完成时将有限的 recent turns 或 episodic facts 写入 MemoryStore
```

建议改成：

```text
在 Turn 进入终态后，根据明确的 memory write policy 写入有限的 recent turns 或 episodic facts。
```

原因是“完成时”容易被理解为只写成功 Turn，也可能被理解为任何执行结束。是否记录失败 Turn、拒绝 Turn、timeout Turn，应在 Phase4 技术方案里明确，而 Roadmap 不必提前选定。

# 4. P2：Phase3 应明确只建立逻辑 AgentSession identity，不建立完整状态系统

Phase3 现在同时写了：

```text
建立 AgentSession resolution contract
GameEvent 路由到对应 AgentSession
```

而 Phase4 又写：

```text
建立最小 AgentSession state boundary
```



实际分层是合理的：

```text
Phase3
    identity / resolver

Phase4
    state / memory
```

但文字上“路由到对应 AgentSession”容易让开发者认为 Phase3 就需要实现完整：

```text
AgentSession object
Session registry
Session state
Lifecycle store
```

建议统一为：

```text
Phase3
    AgentSessionIdentity
    AgentSessionResolver
    minimal active-turn guard

Phase4
    AgentSession state boundary
    MemoryStore
```

### 建议替换 Phase3 范围中的两处文字

原文：

```text
GameEvent 携带目标 entity 信息，Runtime 通过 identity contract 解析并路由到对应 AgentSession。
```

建议：

```text
Runtime 基于现有 GameEvent entity 信息和 Environment / World scope，
解析出稳定 AgentSessionIdentity，并将事件路由到该逻辑身份对应的 Turn 控制边界。
```

原文：

```text
同一 AgentSession 同时只允许一个 active Turn。
```

建议：

```text
同一 AgentSessionIdentity 对应的逻辑 Agent 同时只允许一个 active Turn；
Phase3 只实现满足该不变量的最小内存控制，不引入完整 AgentSession state。
```

这还有一个好处：避免“GameEvent 携带目标 entity 信息”被误解为 Phase3 默认需要修改 proto。当前 Phase1 已经存在事件实体信息；Phase3 的重点应该是泛化解析与路由，而不是默认新增协议字段。

# 5. P2：Phase6 ADR 的进入门表述需要统一

Phase6 的主要范围写：

```text
开发前完成 Async Action Protocol Strategy ADR
```

阶段依赖门又写：

```text
进入 Phase6 开发前
Async Action Protocol Strategy ADR 必须 Accepted
```



语义大体正确，但会出现一个形式问题：

> ADR 到底是 Phase6 的交付物，还是进入 Phase6 之前已经完成的交付物？

建议统一为：

```text
ADR 属于 Phase6 Planning / Entry Gate，
不是 Phase6 implementation 过程中的普通开发任务。
```

### 建议修改为

Phase6 主要范围开头：

```markdown
- Phase6 技术方案定稿和代码实现开始前，必须先完成并 Accepted `Async Action Protocol Strategy ADR`；
```

阶段依赖门：

```text
进入 Phase6 implementation 前
    Async Action Protocol Strategy ADR 必须 Accepted。
```

Phase6 完成条件里不必再把：

```text
ADR 已 Accepted
```

作为功能完成条件重复一次，可以改成：

```text
Phase6 实现符合已 Accepted ADR 所确定的 Protocol 与 continuation 策略。
```

# 不需要再改的部分

以下部分现在已经足够明确，不建议继续扩充。

## Phase3 Identity Contract

这一部分已经写得很好：

```text
GameScope
+
WorldScope
+
StableEntityIdentity
```

并且明确排除了：

```text
session_id
display_name
本地化名称
```

还有覆盖不同 entity、不同 world、不同 session 和显示名称变化的验收矩阵。作为 Roadmap 的 P0 contract，详细程度已经足够。

不需要现在进一步冻结：

```text
字符串格式
hash
UUID
数据库主键
entity_type 是否必进 key
```

## Reconnect 继续放在 Phase7

当前安排合理。Phase3 先保证 identity 与 connection 解耦，Phase7 再实现 EnvironmentSession 重建、Capability refresh、pending 收敛和持久状态，依赖关系是清楚的。

## Phase4 TestEnvironment 与 Phase8 MiniWorld

当前分层也合理：

```text
Phase4
    可复用、确定性测试夹具

Phase8
    正式 Scenario Evaluation / MiniWorld / contract tests
```

Phase4 解决的是后续开发可测试性；Phase8 解决的是系统化评估和交付，不需要再移动。

## Phase6 Protocol 策略

优先复用：

```text
execution_mode
ActionStatusUpdate
ActionResult
CancelActionRequest
```

只有 ADR 证明现有 proto 存在缺口时才考虑兼容性或版本升级，这个判断顺序是正确的。

## Phase3–Phase8 的主体顺序

主体顺序仍然成立：

```text
Identity
→ Memory
→ Multi-step
→ Async Action
→ Recovery / Persistence
→ Evaluation / Productization
```

每一阶段都建立在前一阶段的核心 contract 上，也保留了阶段结束后重新 Review 的机制。
