对，而且你这里已经把 **Context 的“静态层”和“存档态层”** 区分出来了。这个区分非常重要。

但我会再精确一点：**不同存档不一定要有一份完全独立的 Agent Profile，而应该是“基础角色定义 + 存档级角色状态”两层叠加。**

可以把整个 Context 模型逐渐整理成下面这样：

```text
Context
│
├── Runtime Policy
│
├── Game Definition
│   └── 固定游戏规则 / 世界设定
│
├── Save World Context
│   └── 当前存档世界进程
│
├── Agent Definition
│   └── 固定角色人格 / 背景
│
├── Agent State
│   └── 当前存档中这个角色的状态
│
├── Memory
│   └── 这个角色在此存档经历过什么
│
├── Observation
│   └── 此刻看到什么
│
└── Event
    └── 为什么这次被唤醒
```

这会比把所有东西都塞进 `GameContext` 或 `AgentProfile` 清楚很多。

------

## 1. `Game Context` 最好进一步拆成两层

你说的非常对。

### Game Definition：固定游戏规则

这是**跨存档共享**的。

key 可以是：

```text
game_id
+
game_version
```

例如 Stardew：

```text
一年四个季节

每个季节 28 天

一天具有固定的游戏时间推进规则

Pelican Town 是主要城镇

不同 NPC 有自己的日程和关系系统

玩家拥有农场

存在节日、商店、天气等系统
```

这些东西：

> 不应该因为玩家开了一个新存档就复制一份。

可以叫：

```text
GameDefinition
WorldRules
GameLore
```

我比较推荐：

```text
GameContext
├── Rules
└── Lore
```

例如：

```yaml
game_id: stardew-valley

calendar:
  seasons:
    - spring
    - summer
    - fall
    - winter
  days_per_season: 28

world:
  main_town: Pelican Town
```

它解决的是：

> **“这个游戏世界通常是怎么运作的？”**

------

## 2. `Save World Context` 才表示这个存档现在发展成什么样

这个是：

```text
game_id + save_id
```

独有的。

例如玩家 A 的存档：

```text
Year 2
Fall 12

Community Center 已完成

Joja 已关闭

玩家已经解锁沙漠

玩家已修复温室

当前小镇发生过某些关键剧情

玩家已经和 Abigail 结婚
```

玩家 B：

```text
Year 1
Spring 8

Community Center 基本没进展

沙漠未解锁

玩家还是单身
```

虽然都是：

```text
Stardew Valley
```

但两个世界实际上已经是：

> **两个不同的世界实例。**

所以我会定义：

```text
Game Definition
=
这个游戏是什么
```

而：

```text
Save World Context
=
这个存档当前变成了什么
```

这个概念非常值得保留。

------

# 3. Agent Profile 同样最好拆两层

这里就是你问的：

> 不同游戏存档应该有不同 Agent Profile 吧？

答案是：

**一半对。**

比如 Linus 的基础人格：

```text
喜欢自然

偏爱独立生活

物质欲较低

性格温和

住在山边
```

理论上：

```text
Save A Linus
Save B Linus
Save C Linus
```

基础人物设定应该一致。

所以它应该是：

```text
Agent Definition
key:
game_id + entity_id
```

例如：

```text
stardew-valley
+
npc:Linus
```

------

但这个存档里的 Linus **当前是什么样**，当然应该不同。

所以再有：

```text
Agent State
key:
game_id + save_id + entity_id
```

例如：

### Save A

```text
Linus

friendship_with_player = 8 hearts

relationship = close friend

current_emotional_state = trusting
```

### Save B

```text
Linus

friendship_with_player = 0 hearts

relationship = stranger
```

因此：

```text
              Linus Agent

        Base Agent Definition
                 │
                 │
       ┌─────────┴─────────┐
       ↓                   ↓

 Save A AgentState     Save B AgentState

  8 hearts              0 hearts
  trusts player          stranger
```

比“每个存档复制一个完整 Agent Profile”更合理。

------

# 4. Memory 再独立一层

然后：

```text
Agent Definition
```

回答：

> 我是谁？

```text
Agent State
```

回答：

> 我现在是什么状态？

```text
Memory
```

回答：

> 我经历过什么？

这三个一定不要混。

例如：

### Agent Definition

```text
Linus 崇尚自然和简单生活。
```

### Agent State

```text
Linus 当前与玩家关系很好。
```

### Memory

```text
Day 15:
玩家送给我一份 Coconut。

Day 18:
玩家在雨天来帐篷附近找我聊天。

Day 22:
玩家帮助我处理了一件事情。
```

你以后做 Memory Retrieval，主要搜索的是第三种。

而不是每次：

```text
vector search
```

去寻找：

> “Linus 是一个喜欢自然的人。”

这种固定人格信息。

------

# 5. 所以最终 Scope 可以非常漂亮

我建议未来直接把这张表写进架构设计：

| Context 类型       | Scope                           |
| ------------------ | ------------------------------- |
| Runtime Policy     | Runtime                         |
| Game Rules / Lore  | `game_id + game_version`        |
| Save World Context | `game_id + save_id`             |
| Agent Definition   | `game_id + entity_id`           |
| Agent State        | `game_id + save_id + entity_id` |
| Agent Memory       | `game_id + save_id + entity_id` |
| Observation        | 当前 AgentRun                   |
| Event              | 当前 AgentRun                   |
| Tools              | 当前 Environment / Entity       |

这样以后看到一个 Context 数据，你第一反应就是：

> **它的生命周期和 Scope 是什么？**

这是很好的 Runtime 设计思维。

# 6. 实际 Build Context 就会变成这样

比如点击 Linus：

```text
game_id   = stardew-valley
save_id   = Farm001
entity_id = npc:Linus
```

ContextBuilder：

```text
                    ContextBuilder
                           │
         ┌─────────────────┼──────────────────┐
         ↓                 ↓                  ↓
GameDefinition      SaveWorldContext     AgentDefinition
 game_id             game+save           game+entity
                                             │
                                             ↓
                                        AgentState
                                       game+save+entity
                                             │
                                             ↓
                                           Memory
                                       game+save+entity

                           │
                           ↓
                     Observation
                           +
                        Event
                           +
                        Tools
                           ↓
                    Model Request
```

伪代码以后可能长成：

```go
func (b *ContextBuilder) Build(
    ctx context.Context,
    run RunContext,
) (*ModelContext, error) {

    game := b.games.Get(
        run.GameID,
    )

    world := b.worlds.Get(
        run.GameID,
        run.SaveID,
    )

    profile := b.agents.GetDefinition(
        run.GameID,
        run.EntityID,
    )

    state := b.agents.GetState(
        run.GameID,
        run.SaveID,
        run.EntityID,
    )

    memories := b.memory.Search(
        run.GameID,
        run.SaveID,
        run.EntityID,
        run.Event,
    )

    // combine...
}
```

这已经非常接近未来成熟的 Context Engine。

# 7. 但是 Save World Context 有个重要问题

这里不要把：

```text
整个游戏存档
```

完整塞给 LLM。

比如 Stardew 存档里以后可能有：

```text
几百个任务
几十个 NPC
所有物品
所有关系
所有剧情 flag
所有地图状态
……
```

全部进入 Context 肯定不合理。

所以你可以再区分：

```text
Persistent World State
```

和：

```text
Relevant World Context
```

也就是：

```text
完整 Save State
        ↓
Context Selector
        ↓
与本次 AgentRun 有关的信息
        ↓
LLM
```

比如 Linus 对话不一定需要知道：

```text
玩家仓库第 37 格有什么。
```

但可能需要：

```text
当前年份
季节
关键剧情状态
当前节日
玩家与 Linus 的关系
最近世界事件
```

所以以后 `ContextBuilder` 真正有价值的地方，不只是：

> 拼 Prompt。

而是：

> **根据当前 AgentRun 决定哪些世界信息值得进入模型上下文。**

------

# 8. Save World Context 从哪里来？

这里也有两个来源。

### Adapter Observation

适合**实时状态**：

```text
current_time
weather
location
nearby_entities
friendship
```

因为这是游戏当前真实状态。

### Runtime 持久化 World Context

适合**长期语义状态**：

```text
Community Center completed

某条关键剧情已经发生

玩家已经成为某人的配偶

小镇目前处于某个故事阶段
```

不过这里长期来看需要很谨慎：

> **游戏本身应该仍然是真实状态 Source of Truth。**

Runtime 不应该自己维护一份：

```text
Community Center = completed
```

然后游戏里其实没完成。

更合理的是：

```text
Game Save
= Ground Truth

Adapter
↓
抽取重要 World State

Runtime
↓
保存 / 摘要 / 索引
```

Runtime 那份是：

> 面向 Agent Context 的 representation。

而不是另一个游戏存档系统。

------

# 9. 这样你甚至会自然得到一个非常好的四层世界模型

我觉得以后可以把它正式叫：

```text
Game Definition
       ↓
World Instance
       ↓
Agent Instance
       ↓
Agent Memory
```

对应：

```text
Game Definition
Stardew 是怎样的游戏
```

↓

```text
World Instance
Farm001 当前发展成什么样
```

↓

```text
Agent Instance
Farm001 中的 Linus 当前是什么状态
```

↓

```text
Agent Memory
Farm001 Linus 经历过什么
```

这个模型非常通用。

换 Minecraft 也是：

```text
Minecraft Definition

↓
World Save #123

↓
Villager #456

↓
Villager #456 Memory
```

换 RimWorld 也是一样。

所以这不仅不会损害 GameAgent 的通用性，反而**恰好是通用框架应该提供的 Context Scope 模型**。

# 10. 我会稍微修改之前说的目录

之前简单说：

```text
games/stardew-valley/
```

现在更准确可以是：

```text
games/
└── stardew-valley/
    ├── game.yaml
    ├── lore/
    │   └── world.md
    │
    └── agents/
        ├── linus.yaml
        └── abigail.yaml
```

这里放：

```text
Game Definition
Agent Definition
```

而动态内容不要放这里。

动态数据进入：

```text
Runtime Storage
```

逻辑 namespace：

```text
saves/
└── Farm001/
    ├── world_state
    │
    └── agents/
        └── npc:Linus/
            ├── state
            └── memory
```

不代表以后一定用目录存，只是逻辑关系。

实际上后面大概率进数据库。

## 所以你现在的理解可以进一步精炼成这句话

不是简单：

> 不同存档有不同 Profile 和不同 Game Context。

而是：

> **静态定义与动态实例分离。**

具体：

```text
Game Definition
        +
Save World State

Agent Definition
        +
Save-scoped Agent State
        +
Save-scoped Memory

        ↓
Current Observation
        ↓
Agent Context
```

这套设计我认为比单纯：

```text
每个 game_id 一个 prompt
每个 NPC 一个 memory
```

高一个层次，也更符合你后面想真正学习 Harness / Runtime Context Engineering 的目标。

但依旧建议：**现在只把这个模型记下来，不改 MVP0。** 等 MVP0 的 `buildPrompt()` 真正开始成为瓶颈时，再把它重构成第一版 `ContextBuilder`，到那个节点你会非常自然地理解为什么需要这些 Scope。
