# 一、先把“复杂”分成两件事

你现在的 Context 有这么多层：

```text
Runtime Policy
Game Rules / Lore
World Instance Context
Agent Definition
Agent State
Agent Memory
Observation
Event
Tools
```

第一眼确实会觉得多。

但它们本质上不是九套系统，而是在回答九个不同的生命周期问题。

比如你现在这张表：

| Context           | Scope                 |
| ----------------- | --------------------- |
| Runtime Policy    | Runtime               |
| Game Rules / Lore | game                  |
| World Instance    | game + world          |
| Agent Definition  | game + entity         |
| Agent State       | game + world + entity |
| Agent Memory      | game + world + entity |
| Observation       | AgentRun              |
| Event             | AgentRun              |
| Tools             | Environment / Entity  |

真正的价值其实是：

> **数据属于谁、活多久、什么时候失效。**

这个问题不管是 Stardew、Minecraft、RimWorld，甚至非游戏 Agent 都存在。

所以从**概念模型**来说，我反而建议保留这种层次。

真正会变成过度设计的是：

```text
RuntimePolicyManager
GameLoreManager
WorldContextManager
AgentDefinitionManager
AgentStateManager
MemoryManager
ObservationManager
EventManager
ToolContextManager
...
```

然后每一个都有：

```text
Provider
Repository
Resolver
Cache
Factory
Registry
Service
```

这才会爆炸。

所以我建议：

> **Context taxonomy 可以完整，第一版实现必须很薄。**

例如 Phase4 第一版甚至完全可以只是：

```go
type ModelContext struct {
    RuntimePolicy   ...
    GameContext     ...
    WorldContext    ...
    AgentDefinition ...
    AgentState      ...
    Memories        ...
    Observation     ...
    Event           ...
    Tools           ...
}
```

然后：

```go

```

里面简单组装。

先不要因为有九种 Context，就造九个 subsystem。

那么：

这就是我认为你应该坚持的设计标准。

而目前你的架构**基本已经站在这条路上**。现在最值得做的不是简化 Context，而是把 `Agent Definition = entity` 这个假设再抽象半步，并且尽早增加一个“非 Stardew 语义”的 Fake Adapter contract test。做到这两个，你会对“这东西到底是不是真的 game-independent”有非常强的工程证据，而不只是架构文档上的自洽。

你的理解基本对，但我会修正一个关键点：

> **问题确实是 `Agent Definition = game_id + entity_id` 隐含了“Entity 是预定义角色”的假设。**
>
> 但我不建议把解决方案简单定义成“Adapter 主动注册 Agent Definition”。更好的抽象是：**Agent Definition 从静态配置，升级成“可解析的 Agent 描述”，静态配置只是其中一种来源。**

这两者差别很重要。

## 1. Stardew 现在为什么成立

星露谷是：

```text
game_id = stardew
entity_id = npc:Abigail
```

Runtime 可以提前有：

```text
AgentDefinition {
    name: Abigail
    personality: ...
    background: ...
    prompt: ...
}
```

所以：

```text
(game_id, entity_id)
        ↓
static config
        ↓
AgentDefinition
```

完全成立。

但 Minecraft / RimWorld 这种生成式 Entity：

```text
world_001
pawn:723491
```

这个 Pawn 可能刚刚随机生成。

Runtime 在启动时根本不知道：

```text
pawn:723491
```

将会存在。

所以问题不是简单的“缺少注册 API”，而是：

> **Agent Definition 不应该天然等于静态 Runtime Configuration。**

```text

=

+
```

这样一下就通用了。

# 3. 所以我不建议把 Definition Scope 定成 `game_id + entity_id`

更合理的 Scope 是：

| Context                      | Scope                            |
| ---------------------------- | -------------------------------- |
| Agent Definition / Archetype | `game_id + definition_id`        |
| Agent Instance Descriptor    | `game_id + world_id + entity_id` |
| Agent State                  | `game_id + world_id + entity_id` |
| Agent Memory                 | `game_id + world_id + entity_id` |

例如 Stardew：

```text
entity_id     = npc:Abigail
definition_id = npc:Abigail
```

它刚好 1:1，所以看不出区别。

Minecraft：

```text
entity_id     = villager:uuid-123
definition_id = villager/farmer
```

RimWorld：

```text
entity_id     = pawn:723491
definition_id = human_pawn
```

甚至游戏可以生成一个特殊 NPC：

```text
entity_id     = npc:uuid-999
definition_id = bandit_leader
```

这样 Runtime 根本不需要提前知道具体 `entity_id`。

```text
Adapter.GetAgentDescriptor(...)
    ↓
{
  entity_id: "pawn:723491",
  definition_id: "human_pawn",
  name: "Alice",
  traits: [...]
}
    ↓
DefinitionResolver("human_pawn")
    ↓
AgentSession
```

这比：

```text
Adapter:
RegisterAgent(...)
RegisterAgent(...)
RegisterAgent(...)
```

更干净。

因为主动注册会带来很多同步问题：

```text
什么时候注册？
spawn 时？
加载存档时？
Runtime reconnect 后怎么办？
漏掉注册怎么办？
entity despawn 怎么注销？
一个 world 有 10 万 Entity 怎么办？
```

所以我更推荐：

> **Lazy Resolve 为主，主动注册为可选优化。**

也就是说：

```text
第一次真正需要运行这个 Agent
↓
Runtime 向 Adapter 查询
↓
解析 Descriptor
↓
创建 / 获取 AgentSession
```

如果未来某些游戏天然有：

```text
entity_spawned
entity_destroyed
```

事件，可以利用它做 cache warmup / invalidation，但这不应该成为 correctness 的基础。

------

# 5. 甚至不是所有 Entity 都应该成为 Agent

这个问题也很重要。

Minecraft 可能存在：

```text
100 sheep
300 zombies
200 villagers
1000 items
```

显然不能：

```text
每个 entity_id
=
一个完整 AgentSession + Memory + LLM
```

所以 Adapter 返回的信息里最好还有一个概念：

```text
Agent Eligibility
```

或者由 Runtime Policy 决定：

```text
Entity
↓
Agent Binding / AgentResolver
↓
Is Agent?
```

例如：

```text
cow:123
→ no agent

villager:456
→ lightweight agent

important_npc:789
→ full persistent agent
```

因此长期来看我甚至更喜欢这个模型：

```text
Game Entity
      │
      ↓
Agent Binding
      │
      ├── none
      └── Agent Instance
             │
             ├── Definition
             ├── State
             └── Memory
```

也就是说：

> **Game Entity 和 Agent 不应该理论上强制 1:1。**

星露谷只是基本接近 1:1。

------

# 6. 除了 Agent Definition，还有几个地方确实需要注意

目前我认为不是“大问题”，而是第二游戏接入前需要明确的几个 contract。

### 第一：`entity_id` 必须是“稳定身份”，不能只是当前对象 ID

你现在的 AgentSession identity 思路：

```text
game_id
+ world_id
+ entity_type
+ stable_entity_id
```

这个方向一定要坚持。

因为很多游戏内部的：

```text
entity_id = 37
```

可能只是 runtime handle。

游戏重载之后：

```text
37
```

可能变成另一个 NPC。

如果 Memory 绑定这个 ID：

```text
NPC A memory
↓
错误绑定到 NPC B
```

问题会很严重。

所以 Adapter contract 应该要求：

> `stable_entity_id` 在当前 world identity 生命周期内稳定。

如果游戏本身做不到，Adapter 必须建立映射。

------

## 第二：World 生命周期仍然要定义清楚

`world_id` 很通用，但有一个边界问题：

比如 roguelike：

```text
save slot
run
level
```

哪个是 world？

Minecraft：

```text
server
world
dimension
```

哪个是 world？

所以不要规定 world 是某个游戏概念。

应该规定语义：

> **world_id 是 Agent State / Memory / Entity Identity 的持久化命名空间。**

只要满足：

```text
换 world_id
→ 默认视为另一套 Agent Instance State / Memory
```

就够了。

具体 Adapter 自己决定：

```text
Stardew → save
Minecraft → world/save
RimWorld → colony save
某 Roguelike → run
```

------

## 第三：Observation 不要继续“统一字段”

这个依然是第二个最大的风险。

例如从 Stardew 开始很容易变成：

```text
Observation {
    location
    season
    weather
    friendship
}
```

接 Minecraft：

```text
biome?
health?
hunger?
blocks?
```

然后不断扩协议。

应该坚持：

```text
Generic Envelope
+
Game-specific Payload
```

Runtime 只需要真正跨游戏的东西：

```text
world
entity
revision
timestamp
perhaps nearby entity refs
```

而不是理解：

```text
season
mood
hunger
mana
job
```

Context Engine 可以消费这些结构化数据，但 Runtime Core 不应该依赖它们的具体语义。

------

## 第四：Trigger 也不能是 Stardew Event 枚举

现在你 Phase3 暂时保留：

```text
player_interacted_with_npc
```

没问题。

但最终：

```text
GameEvent
↓
Trigger Router
↓
AgentRun
```

必须允许完全不同的游戏：

```text
player_interacted
damage_received
enemy_spotted
goal_due
conversation_started
time_elapsed
world_event
```

核心 AgentLoop 不应该写：

```go
if event.Type == "player_interacted_with_npc"
```

这个你后续已有 Trigger Router 的方向，所以主要是落实，不需要重新设计。

------

## 第五：Capability 应该是动态的，而不只是 Entity 固定属性

例如一个 Minecraft Agent：

```text
平时：
move
talk
inspect

拿到镐以后：
mine

进入战斗以后：
attack

死亡以后：
none
```

所以长期最好认为：

```text
Available Tools
=
ResolveCapabilities(
    environment,
    agent,
    current_state,
    policy
)
```

而不是：

```text
entity_type = villager
→ 永远固定这些工具
```

这一点与你现在的 Capability → Tool 动态生成路线其实是一致的。

------

# 7. 我会把整个模型最终画成这样

这其实比“Adapter 主动注册 Agent”更完整：

```text
                   Game / Environment
                          │
                    entity_id
                          │
                          ▼
                    Agent Resolver
                          │
              ┌───────────┴───────────┐
              │                       │
          not an agent           Agent Binding
                                      │
                          ┌───────────┴────────────┐
                          │                        │
                  definition_id           instance descriptor
                          │                        │
                          ▼                        │
                  Agent Definition                │
                          │                        │
                          └──────────┬─────────────┘
                                     ▼
                               Agent Instance
                                     │
                         ┌───────────┼───────────┐
                         ▼           ▼           ▼
                       State       Memory     Capabilities
                                     │
                                     ▼
                                  AgentRun
                                     │
                                     ▼
                               Context Engine
```

这里最大的变化只有两个：

```text
Entity ≠ Agent Definition
Entity → Agent Binding
```

和：

```text
Agent Definition ≠ Agent Instance
```

------

# 8. Context 的整体 Scope 因此可以升级成这一版

我认为这可能就是你现在最成熟的一版：

| Context 类型              | Scope                            | 含义                     |
| ------------------------- | -------------------------------- | ------------------------ |
| Runtime Policy            | Runtime                          | Harness 全局约束         |
| Game Rules / Lore         | `game_id + game_version`         | 游戏共同规则             |
| World Context             | `game_id + world_id`             | 当前世界实例             |
| Agent Definition          | `game_id + definition_id`        | 可复用角色/Agent 模板    |
| Agent Instance Descriptor | `game_id + world_id + entity_id` | 当前世界中的具体角色身份 |
| Agent State               | `game_id + world_id + entity_id` | 当前动态状态             |
| Agent Memory              | `game_id + world_id + entity_id` | 长期经历                 |
| Observation               | 当前 AgentRun                    | 当前感知                 |
| Event / Trigger           | 当前 AgentRun                    | 为什么这次运行           |
| Tools                     | 当前 AgentRun                    | 当前真正允许的能力       |

这版比你原来复杂**一个概念**，但实际上能避免以后非常大的复杂度。

因为你不再强迫：

```text
static definition
dynamic identity
dynamic attributes
```

全部塞到 `AgentDefinition` 里面。

------

# 9. 一个很重要的原则：不要让 Adapter 决定全部 Agent Prompt

这里也容易走偏。

既然动态角色来自 Adapter，很容易最后变成：

```text
Adapter.GetAgentDefinition()
→ 返回完整 system prompt
```

我不推荐。

更好的职责划分：

**Adapter 提供事实：**

```text
entity_id
definition_id
name
traits
game attributes
state
```

**Runtime / Context Sources 提供 Agent 行为定义：**

```text
definition_id = human_pawn
→ base agent policy
→ role prompt
→ personality interpretation rules
```

然后 ContextEngine 组合。

这样游戏 Adapter 仍然只是：

> Environment semantics translator

而不会逐渐变成：

> Agent framework implementation。

这是你整个项目能不能保持 narrow waist 的关键。

------

所以，回到你最开始的问题：

**是的，你已经准确发现了现在 Context 设计里最明显的 Stardew-specific 假设。**

但我会把解决方式从：

```text
Adapter 主动注册 Agent Definition
```

调整成：

```text
Adapter / Environment
      ↓
按需提供 Agent Instance Descriptor

Runtime
      ↓
根据 definition_id 解析 Agent Definition
```

主动注册可以支持，但最好只是优化机制，不是核心 contract。

而除了这个，目前我认为还需要重点守住四条边界：**stable entity identity、world namespace、Observation 不膨胀成万能 schema、Trigger/Capabilities 动态化。**

这些都守住以后，你现在这套 Context + Loop 架构就不是“为 Stardew 抽象”，而是真的开始接近一个 game-independent Agent Harness。
